# RPA 学习进度每周统计模块设计

- 日期：2026-07-22
- 状态：已批准
- 项目：AI Tools web / RPA 项目管理系统

## 1. 背景与目标

系统需要增加“RPA 学习进度每周统计”模块。实习生每周填写一条学习周报，HR 和老板按周查看提交情况、汇总指标、人员明细及个人历史趋势，并负责人员角色维护。

该模块必须满足以下边界：

1. 生产 MySQL `users` 表保持只读，不增加字段、不建表、不修改用户数据。
2. 角色、周名单、周报和审计数据复用现有本地 SQLite `assets.db`。
3. 新模块实施真实的服务端权限校验；现有其他模块暂不统一改造鉴权。
4. 普通员工不显示新模块入口，也不能访问新模块接口。

## 2. 已确认的业务规则

### 2.1 角色

角色共四种：

- `employee`：普通员工。
- `intern`：实习生。
- `hr`：HR。
- `boss`：老板。

MySQL `users.id` 是本地角色映射的稳定关联键。没有本地角色映射的账号默认按普通员工处理，登录时不自动创建映射。

HR 和老板都可以分配全部四种角色，也可以查看角色变更历史。系统不强制保留最后一个老板，允许暂时没有 HR 或老板。

首次老板账号通过环境变量 `INITIAL_BOSS_EMAILS` 配置，支持以逗号分隔多个已注册邮箱。启动时只为尚无角色映射的匹配账号创建老板映射，不覆盖之后的人工角色调整；未匹配邮箱写入服务日志。

### 2.2 周期与周名单

- 每周周期为周一 00:00 至下一周一 00:00，业务时区固定为 `Asia/Shanghai`。
- 所有操作时间在 SQLite 中按 UTC 保存，接口序列化时转换为 `Asia/Shanghai`；周起止日期和退回截止时间均按上海时区解释后再转换为 UTC。
- 每位实习生每周最多一条工作周报。
- 每周应提交人员使用周名单快照，快照生成后不因周中角色调整而变化。
- 新设置的实习生从下一个周一进入应提交名单。
- 周中被调整为其他角色的实习生仍需完成本周周报，从下一周退出名单。
- HR 和老板的管理权限按当前角色立即生效；实习生当前周的填报资格以周名单为准。

### 2.3 周报字段

周报包含：

- 学习内容：必填文本。
- 学习时长：必填，范围 `0–168` 小时，最多一位小数。
- 完成度：必填，`0–100` 的整数百分比。
- 备注：选填文本。

保存草稿时允许字段暂未填写完整；正式提交时才强制执行上述必填、范围和精度校验。

### 2.4 草稿、提交与锁定

- 当周支持保存草稿和正式提交。
- 草稿计入未提交，不参与汇总统计。
- 正式提交后，当周仍可继续编辑并再次提交。
- 正式版本与可编辑工作副本分开保存。
- 已正式提交后产生的新修改标记为“有未提交修改”；统计继续使用上一次正式版本。
- 再次正式提交会生成新版本，并替换统计使用的正式版本。
- 到下一周一时自动锁定。若存在尚未再次提交的修改，锁定上一次正式版本；未提交修改不进入统计。
- 只有草稿而从未正式提交的周报在周一后保持未提交并锁定。

### 2.5 退回修改

- HR 或老板只能查看周报，不能直接编辑实习生内容。
- 已锁定且存在正式版本的周报可以被退回。
- 退回时必须填写原因并选择修改截止时间。
- 退回原因展示给实习生，所有退回操作永久保留历史。
- 退回期间状态为“退回修改中”，按未提交处理，并从汇总指标中排除。
- 实习生在截止时间前重新提交后立即锁定，生成新的正式版本并恢复统计。
- 超过截止时间仍未提交时自动锁定并标记“退回逾期”，继续排除统计。
- HR 或老板可以再次退回逾期记录并设置新的原因和截止时间。

### 2.6 统计口径

HR 和老板的统计页包含：

- 周选择器。
- 已提交人数。
- 未提交人数。
- 已提交记录的总学习时长。
- 已提交记录的平均完成度。
- 实习生明细表。
- 个人历史趋势。

已提交人数只包括当前存在有效正式版本、且不处于“退回修改中”或“退回逾期”的周报。未提交人数为周名单人数减去已提交人数。

总学习时长和平均完成度只计算有效正式版本。平均完成度的分母为有效正式提交人数；没有有效提交时返回 `null`，前端显示 `—`，不显示误导性的 `0%`。

个人趋势默认展示最近 12 周，并允许选择起止周查看全部历史。学习时长使用柱形，完成度使用折线；被退回修改或退回逾期的周次显示为空档，不进入趋势值。

| 查看学习周报入口 | 否 | 是 | 否 | 否 |
| 保存本人当前周草稿 | 否 | 是 | 否 | 否 |
| 提交本人当前周周报 | 否 | 是 | 否 | 否 |
| 查看本人历史 | 否 | 是 | 否 | 否 |
| 查看全员每周统计 | 否 | 否 | 是 | 是 |
| 查看个人趋势 | 否 | 否 | 是 | 是 |
| 退回锁定周报 | 否 | 否 | 是 | 是 |
| 查看人员权限 | 否 | 否 | 是 | 是 |

## 4. 总体架构

### 4.1 前端入口

用户工作台新增：

- `/main/LearningReport`：学习周报，仅实习生或当前周名单成员显示。

管理后台新增：

- `/admin/LearningStats`：学习统计，仅 HR 和老板显示。
- `/admin/RoleManagement`：人员权限，仅 HR 和老板显示。

路由继续采用懒加载。工作台栏目列表改为基于 `/learning/me` 返回的权限动态计算。前端隐藏入口只是体验层；后端仍独立校验所有请求。

### 4.2 后端边界

新增 `/learning` Blueprint，集中处理：

- 当前身份和周资格。
- 草稿、提交和个人历史。
- 周统计和个人趋势。
- 退回操作。
- 人员列表、角色修改和角色审计。

新增学习模块专用鉴权层。现有 `/user/login` 和 `/admin/login` 在验证原账号密码成功后，追加返回学习模块签名令牌和当前角色。现有其他业务接口保持原行为。

### 4.3 数据边界

- MySQL `users`：只读，用于登录、人员列表、显示姓名/邮箱，以及解析 `INITIAL_BOSS_EMAILS`。
- SQLite `assets.db`：继续使用现有 `assets` bind，新增学习模块表。
- 原 `assets` 表及资产接口不改变语义。

## 5. 鉴权设计

学习模块令牌使用现有依赖 `itsdangerous` 进行签名，默认有效期 12 小时。令牌只承载 `user_id`、签发时间和用途标识，不承载可信角色；每个受保护请求均从 `assets.db` 重新读取当前角色，因此管理权限变更可立即生效。

令牌密钥优先读取环境变量 `LEARNING_TOKEN_SECRET`。若未配置，服务首次启动时在 `backend/var/learning_token_secret.key` 生成并持久化随机密钥，后续重启复用。密钥文件不得由接口返回或写入日志。

前端在登录成功后保存学习令牌；请求 `/learning/*` 时通过共享 `src/api/http.js` Axios 实例添加 `Authorization: Bearer <token>`。前端不得用请求参数传递可信 `user_id` 或角色。

响应约定：

- `401`：令牌缺失、无效或过期，前端清除令牌并引导重新登录。
- `403`：角色或周资格不满足，前端返回工作台并提示无权限。
- `409`：状态已变化或并发冲突，前端刷新最新记录。
- `422`：字段校验失败，前端保留工作副本并显示具体错误。

## 6. SQLite 数据模型

所有新模型设置 `__bind_key__ = 'assets'`。

### 6.1 `user_roles`

| 字段 | 说明 |
| --- | --- |
| `user_id` | 主键，对应 MySQL `users.id`，不建立跨库外键 |
| `role` | `employee / intern / hr / boss` |
| `assigned_by_user_id` | 最近操作人；系统初始化时为空 |
| `created_at` | 创建时间 |
| `updated_at` | 最近更新时间 |

### 6.2 `role_change_logs`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `target_user_id` | 被调整账号 |
| `old_role` | 调整前角色；无映射时记录 `employee` |
| `new_role` | 调整后角色 |
| `operator_user_id` | HR/老板操作人；初始化记录为空 |
| `source` | `manual` 或 `bootstrap` |
| `changed_at` | 操作时间 |

日志只追加，不更新和删除。角色映射更新与审计插入必须在同一 SQLite 事务中完成。

### 6.3 `weekly_roster_weeks` 与 `weekly_rosters`

`weekly_roster_weeks` 是周快照头表：

| 字段 | 说明 |
| --- | --- |
| `week_start` | 主键，周一日期 |
| `created_at` | 快照生成时间 |

头表允许系统明确记录“本周名单已冻结但人数为零”，防止周中新增实习生被错误加入空名单。

`weekly_rosters` 是快照成员表：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `week_start` | 周一日期 |
| `user_id` | 当周应提交账号 |
| `created_at` | 快照生成时间 |

`weekly_rosters.week_start` 关联快照头表；对 `(week_start, user_id)` 建立唯一约束和按 `week_start` 查询索引。

当前周名单在应用启动和所有角色变更前执行“存在则复用、不存在则创建”。角色只能通过服务接口修改，因此角色变更前一定先冻结当前周名单。其他学习接口也会幂等地确保当前周名单存在。

### 6.4 `weekly_reports`

该表保存可编辑工作副本和当前状态。

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `week_start` | 所属周 |
| `user_id` | 实习生账号 |
| `content` | 工作副本学习内容 |
| `hours_tenths` | 工作副本学习时长，以十分之一小时为单位的整数，范围 `0–1680` |
| `completion` | 工作副本完成度 |
| `remark` | 工作副本备注 |
| `draft_revision` | 每次保存工作副本递增 |
| `latest_submission_id` | 最近有效正式版本，可空 |
| `state` | `draft / submitted / returned / return_expired` |
| `created_at` | 创建时间 |
| `updated_at` | 最近保存时间 |

对 `(week_start, user_id)` 建立唯一约束。是否可编辑由周时间、周名单和退回截止时间共同计算，不依赖前端状态。

### 6.5 `weekly_report_submissions`

该表保存不可变正式版本。

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `report_id` | 所属工作副本 |
| `source_revision` | 提交时的工作副本版本 |
| `content` | 提交快照 |
| `hours_tenths` | 提交快照，以十分之一小时为单位的整数 |
| `completion` | 提交快照 |
| `remark` | 提交快照 |
| `submitted_at` | 提交时间 |

正式提交在同一事务中完成三件事：插入提交版本、更新 `latest_submission_id`、将状态更新为 `submitted`。统计仅读取 `latest_submission_id` 指向的版本。

当 `draft_revision` 大于最新正式版本的 `source_revision` 时，前端显示“有未提交修改”。周一锁定时不需要复制数据，继续使用最近正式版本。

### 6.6 `report_return_logs`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `report_id` | 被退回周报 |
| `returned_by_user_id` | HR/老板操作人 |
| `reason` | 必填退回原因 |
| `edit_deadline` | 修改截止时间 |
| `returned_at` | 退回时间 |
| `resubmitted_at` | 成功重新提交时间，可空 |

退回时将工作副本重置为最近正式版本，避免未提交旧修改成为退回后的起点；`draft_revision` 同步恢复为该正式版本的 `source_revision`，随后状态改为 `returned`。退回期间正式版本仍保留，但统计主动排除该周报。

截止时间过后首次访问相关接口时，服务幂等地将 `returned` 更新为 `return_expired`。不部署额外定时任务。

## 7. 状态流转

### 7.1 当前周

1. 无记录 → 保存 → `draft`。
2. `draft` → 正式提交 → `submitted`，创建第一个正式版本。
3. `submitted` → 继续保存 → 状态仍可序列化为 `submitted`，同时通过修订号显示“有未提交修改”；统计使用原正式版本。
4. 有未提交修改 → 再次正式提交 → 新增版本并更新 `latest_submission_id`。
5. 下一周一后：
   - 有正式版本：锁定最近正式版本。
   - 无正式版本：保持未提交并锁定工作副本。

### 7.2 历史退回

1. 已锁定正式周报 → HR/老板填写原因与截止时间 → `returned`。
2. `returned` → 截止前重新提交 → 新增正式版本、填写当前退回日志的 `resubmitted_at`、状态恢复 `submitted`，并立即锁定。
3. `returned` → 超过截止时间 → `return_expired`。
4. `return_expired` → HR/老板再次退回 → 新增退回日志并回到 `returned`。

## 8. API 设计

所有接口前缀为 `/learning`，除登录接口外均要求 Bearer Token。

### 8.1 当前身份与实习生接口

- `GET /learning/me`
  - 返回当前角色、是否为本周名单成员、可见模块、当前周起止日期和当前周报摘要。
- `GET /learning/reports/current`
  - 返回当前周工作副本、最近正式版本、是否有未提交修改、可编辑状态和退回信息。
- `PUT /learning/reports/current/draft`
  - 保存当前周工作副本并递增修订号。
- `POST /learning/reports/current/submit`
  - 校验字段并创建正式版本。
- `GET /learning/reports/history?from_week=&to_week=`
  - 返回本人历史周报、状态和退回信息。
- `GET /learning/reports/<report_id>`
  - 返回本人指定周报；历史记录只有处于有效退回修改期时才返回可编辑权限。
- `PUT /learning/reports/<report_id>/draft`
  - 保存本人处于有效退回修改期的历史周报工作副本。
- `POST /learning/reports/<report_id>/submit`
  - 在退回截止时间前重新提交历史周报；成功后立即锁定并恢复统计。

### 8.2 HR/老板统计接口

- `GET /learning/admin/weekly-stats?week_start=YYYY-MM-DD`
  - 返回周名单、提交状态、汇总指标和实习生明细。
- `GET /learning/admin/users/<user_id>/trend?from_week=&to_week=`
  - 返回个人趋势，默认最近 12 周。
- `POST /learning/admin/reports/<report_id>/return`
  - 请求体包含退回原因和截止时间。

### 8.3 人员权限接口

- `GET /learning/admin/users?query=&page=&per_page=`
  - 分页读取 MySQL 用户并合并本地角色，绝不返回密码。
- `PATCH /learning/admin/users/<user_id>/role`
  - 修改角色并写入审计。
- `GET /learning/admin/role-change-logs?page=&per_page=`
  - 返回角色变更历史并补充操作人、目标账号显示信息。

## 9. 前端设计

### 9.1 `LearningReport.vue`

页面包含：

- 当前周日期与状态提示。
- 学习内容、学习时长、完成度和备注表单。
- “保存草稿”和“正式提交”两个动作。
- 已提交后的“有未提交修改”提示。
- 退回原因、修改截止时间和逾期提示。
- 历史周报列表，可展开查看正式版本和退回历史。

输入数据在前端做即时校验，但后端始终重复校验。接口失败时不清空表单。

### 9.2 `LearningStats.vue`

采用已批准的单页纵向布局：

1. 周选择器。
2. 已提交、未提交、总学习时长、平均完成度四张统计卡。
3. 实习生明细表，展示状态、时长、完成度、更新时间和操作。
4. 点击人员后在表格下方展开个人趋势。
5. 趋势图使用学习时长柱形与完成度折线，默认最近 12 周，支持起止周筛选。
6. 锁定正式周报提供“退回修改”对话框，强制填写原因和截止时间。

图表优先使用轻量 SVG/Vue 组件实现，不引入重量级图表依赖；若实现阶段证明可维护性不足，再在计划中明确引入依赖。

### 9.3 `RoleManagement.vue`

页面包含人员搜索、分页表格、当前角色下拉选择和角色审计记录。修改角色前显示确认框；成功后刷新当前用户角色和审计列表。

### 9.4 路由与导航

- 新路由全部懒加载。
- `UserView.vue` 和 `AdminView.vue` 根据 `/learning/me` 动态追加栏目。
- 路由守卫在进入新页面时检查学习令牌与服务端权限。
- 普通员工不显示入口；手工输入 URL 时由守卫和后端双重阻止。

## 10. 异常、并发与数据一致性

- 保存草稿和提交时携带当前 `draft_revision`。服务端发现版本不一致时返回 `409`，防止多个标签页静默覆盖。
- 角色修改、角色审计写入同一事务。
- 正式版本插入、报告指针更新和退回完成标记写入同一事务。
- SQLite 操作失败统一回滚，不返回部分成功。
- 用户在 MySQL 中不存在时，角色修改返回 `404`。
- 统计周参数必须是周一；非法日期返回 `422`。
- 截止时间必须晚于当前时间；退回当前周可编辑记录或没有正式版本的记录返回 `409`。
- API 接收最多一位小数的小时值，后端转换为 `hours_tenths` 整数存储和汇总，响应时再转换为小时，避免二进制浮点累计误差。

## 13. 交付成功标准

1. 实习生能够按规则保存草稿、正式提交和处理退回。
2. HR/老板能够查看准确的周统计、明细和个人趋势。
3. HR/老板能够分配角色并查看完整审计。
4. 普通员工无法看到或调用新模块。
5. 角色管理权限即时生效，周名单在一周内保持稳定。
6. 草稿、正式版本、退回和逾期状态按本规范流转且统计口径一致。
7. 所有新业务数据仅写入 `assets.db`，MySQL 保持只读。
8. 后端自动化测试、前端生产构建和浏览器核心流程验证全部通过。
